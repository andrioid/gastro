# Compatibility

gastro is pre-1.0. This page states what an upgrade can change and how
you find out.

## Versioning

gastro follows [semantic versioning](https://semver.org/) with the pre-1.0
convention that the minor version carries breaking changes:

| Change | Bumps | Example |
|---|---|---|
| Bug fix | patch | `v0.4.0` → `v0.4.1` |
| New feature | minor | `v0.4.1` → `v0.5.0` |
| Breaking change | minor | `v0.4.1` → `v0.5.0` |

A patch upgrade is always safe to take. A minor upgrade may require changes
to your project; read its migration guide first.

The `github.com/andrioid/gastro/datastar` module is released in lockstep
with gastro and always carries the same version.

## Breaking changes

Every breaking change ships with:

- a migration guide at `docs/migrations/vX.Y.md`, named after the release
  that introduces the break, listing each change with before/after code;
- a `BREAKING CHANGE:` footer on the commit, so the release notes call it
  out.

There are no deprecation shims. When an API changes, the old form is removed
in the same release and the migration guide explains the replacement; gastro
does not keep the old and the new behaviour side by side.

## Go version

gastro, its generated code, and every project that uses it require the Go
version in gastro's own `go.mod` (currently Go 1.27). `gastro generate`
checks the `go` directive in your module's `go.mod` and stops with a message
naming the required version when it is older.

## Generated code

Every generated Go file in `.gastro/` starts with a header naming the gastro
version that wrote it:

```go
// Code generated by gastro v0.4.0. DO NOT EDIT.
```

Local builds of gastro (a checkout, or a `replace` pointing at a directory)
stamp `(devel)` instead of a version.

Generated code is only guaranteed to work with the gastro version stamped in
its header. The runtime package (`github.com/andrioid/gastro/pkg/gastro`)
and the generated code are one unit: a `.gastro/` tree generated by one
release and compiled against another may not build, or may build and behave
differently. After changing the gastro version in `go.mod`, run
`gastro generate`. If you commit `.gastro/`, `gastro check` reports a tree
whose stamp differs from the running binary as out of date (see
[Deployment](deployment.md#ci-detecting-stale-gastro-gastro-check)).

The simplest way to keep the two in step is the `go tool` install method: the
`tool` directive pins the CLI to the same module version as the runtime.
